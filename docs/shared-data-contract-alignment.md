# Shared Data Contract Alignment

## Authority and scope

The approved **KitaMo Shared Data Contract Baseline v0.1** is the upstream
semantic authority for data shared across Android, Supabase, Admin, and future
analytics systems. The Admin Platform consumes that contract; it does not
redefine merchant accounting, inventory, product, sale, refund, or
synchronization truth.

This mock-first repository implements administrative view contracts only.
They are intentionally not Supabase row definitions. No production migration,
table, relationship, RLS policy, RPC, Clerk mapping, or administrator
assignment source is introduced here.

## Binding rules applied in this iteration

- **Stall is canonical.** Admin routes, models, labels, and relationships use
  `stall`. The legacy Android SQLite term `branch` is not introduced into new
  Admin contracts.
- **Identifiers are opaque.** Mock identifiers are stable fixtures only.
  Production identifiers must follow the shared global-ID strategy and must
  never be inferred, reformatted, or regenerated by the Admin UI.
- **Instants are UTC.** Mock service timestamps are ISO 8601 values with an
  explicit UTC offset. Display conversion happens at the presentation layer.
- **Business timezone is explicit.** Every mock business carries the validated
  IANA timezone `Asia/Manila`. Business detail timestamps are formatted with
  that business timezone. A future adapter must read the authoritative
  business timezone and must not infer it from the administrator's browser.
- **Business date is not an instant.** This UI does not currently expose
  accounting or reporting dates. If a future approved view needs
  `business_date`, it must remain a calendar date interpreted in the
  business's timezone and must not be replaced by a UTC timestamp.
- **Money is excluded.** This iteration has no merchant ledger, transaction,
  sale, refund, expense, profit, tax, or payment detail. A future approved
  financial aggregate must use integer minor units, PHP, and the shared
  calculation/rounding rules; JavaScript floating-point money is prohibited.
- **Quantities and units remain upstream.** Admin does not convert stock or
  recipe units, infer base units, or treat negative stock as invalid.
- **Audit is append-only evidence.** The allowed process-local report update
  creates a mock audit event in the same service use case. The mock store is
  not durable or compliance-grade. Production persistence must follow the
  canonical audit contract and retention/immutability policy.
- **Contract changes are versioned.** A future production adapter must record
  and validate the approved shared contract/schema version. Unknown breaking
  versions fail closed rather than being silently coerced.

## Admin audit view mapping

The current `AuditEvent` is an Admin projection of the canonical audit record.
State snapshots are limited to a small allowlist of redacted scalar values; raw
support-note bodies and unrestricted entity snapshots are prohibited. A
production adapter must map explicitly:

| Shared audit field | Admin view field or behavior                                   |
| ------------------ | -------------------------------------------------------------- |
| `id`               | `id`                                                           |
| `actor_user_id`    | `actorUserId` after verified administrator-principal mapping   |
| `actor_role`       | `actorRole`                                                    |
| `action`           | `action`                                                       |
| `target_type`      | `targetType`                                                   |
| `target_id`        | `targetId`                                                     |
| `business_id`      | `businessId`; nullable only where not applicable               |
| `stall_id`         | `stallId`; nullable only where not applicable                  |
| `reason_code`      | `reasonCode`; closed mock registry pending the shared registry |
| `reason_note`      | `reasonNote`, with support-note minimization and authorization |
| `before_state`     | `beforeState`; bounded, allowlisted, redacted scalar snapshot  |
| `after_state`      | `afterState`; bounded, allowlisted, redacted scalar snapshot   |
| `outcome`          | `outcome`                                                      |
| `occurred_at`      | `occurredAt`; UTC instant displayed in the chosen timezone     |
| `source_ip`        | `sourceIpMasked`; raw values are not exposed                   |
| `device_id`        | `deviceId`; nullable where not applicable                      |
| `app_version_code` | `appVersionCode`; nullable where not applicable                |
| `correlation_id`   | `correlationId`                                                |

The production adapter must preserve required evidence in the source system,
select only fields authorized for the current view, and require an explicit
privacy allowlist for snapshots. Snapshots must never become unrestricted
record dumps.

## Terminology and timestamp mapping

Admin view models currently use UI-oriented camelCase names such as
`lastSeenAt` and `submittedAt`. Before a Supabase adapter is written, each must
be mapped to an inspected canonical source field. The adapter must use the
shared meanings:

- `occurred_at`: when the domain event happened;
- `recorded_at`: when the originating system persisted it;
- `device_created_at`: when an offline-capable client created it;
- `server_received_at`: when the server accepted it;
- `updated_at`: last mutation time;
- `synced_at`: completed synchronization time;
- `business_date`: reporting calendar date in the business timezone.

The mock names do not authorize inventing production columns with those names.

Date-only filters in the global mock Audit Log use `Asia/Manila` calendar-day
boundaries because that is the displayed operational timezone. Audit instants
remain UTC. A future business-scoped audit view must derive its calendar range
from the authoritative business timezone.

## Synchronization event projection

`SyncEvent` is an immutable operational-event projection rather than a device
posture row. Its closed event-name registry is:

- `sync.started`;
- `sync.completed`;
- `sync.failed`;
- `sync.conflict_detected`.

`occurredAt` records the event instant and `syncedAt` is present only when a
successful synchronization completed. Device posture such as the last
successful synchronization remains on the `Device` projection. Each mock event
also carries safe applicable metadata: `appVersionCode`, `platform`, `source`,
opaque entity identifiers, masked network/device identifiers, and a
correlation ID.

`recordsProcessed` counts generic records handled by a completed sync. It does
not mean sales or merchant transactions. The fixture does not invent
`syncBatchId`, `causationId`, `schemaVersion`, or `contractVersion`; those
fields remain gated on the real sync envelope and shared applicability
registry.

## Production integration gate

The shared baseline resolves cross-system semantics but does **not** supply the
physical or authorization contracts needed for production. Before integration,
the team must still inspect:

1. the shared-contract repository and machine-readable schemas/versioning;
2. the known Android models and SQLite migrations plus approved compatibility
   mappings, production sync payloads, and ID transition behavior;
3. the complete Supabase migrations, schema, functions, grants, and RLS
   policies;
4. the Clerk-to-Supabase user mapping and revocation behavior;
5. the authoritative administrator-role assignment source;
6. existing problem-report, synchronization, app-version, and audit storage;
7. audit retention, immutability, failure recording, and access-review rules.

If any source is missing or contradicts the approved baseline, production
adapter work stops with a dependency/conflict report. Mock UI work does not
waive that gate.
